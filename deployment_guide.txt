1. OVERVIEW & ARCHITECTURE
================================================================================

The HBL MRB system consists of these components:

┌─────────────────────────────────────────────────────────────────────┐
│  Browser (React SPA)                                                │
│  └──> Nginx (port 3000) ──> static files from /opt/MRB/frontend/dist│
│  └──> Direct fetch to SAP middleware (port 3002)                    │
│  └──> Supabase API (port 8000) for auth, database, realtime        │
├─────────────────────────────────────────────────────────────────────┤
│  SAP Proxy Middleware  (Node.js, port 3002)                         │
│  └──> Forwards requests to SAP RFC/BAPI endpoints                  │
│  └──> Protected by x-proxy-secret header                           │
├─────────────────────────────────────────────────────────────────────┤
│  Standalone Scheduler  (Node.js, port 3100)                         │
│  └──> Polls sap_api_config for due syncs                           │
│  └──> Uses scheduler_lock to prevent duplicates                    │
│  └──> Supports multi-plant sequential execution                    │
│  └──> Full refresh strategy for MB52 stock data                    │
├─────────────────────────────────────────────────────────────────────┤
│  Supabase (Self-Hosted Docker)                                      │
│  └──> PostgreSQL (port 5432)                                       │
│  └──> PostgREST API (port 8001) via Kong Gateway (port 8000)       │
│  └──> Edge Functions (port 9000)                                   │
│  └──> GoTrue Auth                                                  │
└─────────────────────────────────────────────────────────────────────┘

Key Feature Summary:
  - SAP API integration (MB52, 343, 344, ZMRB01) with dynamic field mapping
  - Manual sync + automated scheduler with configurable frequency
  - Multi-plant support with plant switcher
  - Dynamic role-based access control via database-driven departments table
  - Dynamic workflow routing per plant (configured via UI)
  - MRB approval sequences with role-level routing
  - Pending actions with 7-day SLA logic
  - Material blocking/unblocking via SAP 343/344 APIs
  - MB52 live fetch (no local storage)
  - Email logging and template management
  - Print configuration per plant

4. FRESH INSTALLATION (Step-by-Step)
================================================================================

Prerequisites:
  - Root or sudo access
  - Self-hosted Supabase already running (Docker)
  - SAP middleware source files available

Step 1: Transfer files to server
─────────────────────────────────
  # From your local machine:
  scp -r ./project-root iml@10.10.4.178:/tmp/mrb-source

  # Or clone from git:
  ssh iml@10.10.4.178
  git clone <repo-url> /tmp/mrb-source

Step 2: Run the installer
─────────────────────────
  cd /tmp/mrb-source
  sudo bash deploy/install.sh

  This will:
  ✓ Install Node.js 20, PM2, Nginx, psql client
  ✓ Create /opt/MRB directory structure
  ✓ Copy application files + deploy scripts
  ✓ Generate template .env file
  ✓ Build the frontend
  ✓ Configure Nginx on port 3000 with security headers
  ✓ Configure firewall (SSH + port 3000)
  ✓ Set correct file permissions

Step 3: Configure environment
─────────────────────────────
  sudo nano /opt/MRB/.env

  Fill in ALL values (see Section 5 for details).

Step 4: Setup database
──────────────────────
  sudo bash /opt/MRB/scripts/setup-db.sh

  This will:
  ✓ Enable required PostgreSQL extensions
  ✓ Apply all migration files in order
  ✓ Verify all 27 tables exist
  ✓ Verify all 15 database functions exist
  ✓ Verify departments.workflow_status and role_key columns
  ✓ Report active roles and workflow configs

Step 5: Start services
──────────────────────
  sudo -u iml bash /opt/MRB/scripts/start.sh

  This will:
  ✓ Check Supabase API connectivity
  ✓ Start SAP middleware on port 3002
  ✓ Start standalone scheduler on port 3100
  ✓ Save PM2 process list for reboot persistence

Step 6: Setup scheduler auto-start
───────────────────────────────────
  sudo bash /opt/MRB/scripts/setup-scheduler.sh

  This will:
  ✓ Configure PM2 to auto-start on boot
  ✓ Install cron job for stale lock cleanup
  ✓ Optionally setup pg_cron job

Step 7: Verify installation
───────────────────────────
  sudo bash /opt/MRB/scripts/health-check.sh

  Expected output: All checks should show ✓
  New checks include:
  - Supabase API (port 8000) connectivity
  - Workflow-enabled roles count
  - Plant workflow configuration count
  - Docker/Supabase container status

Step 8: Create admin user
─────────────────────────
  Access the application at http://<SERVER_IP>:3000
  The first user must be created via GoTrue API or SQL:

  -- In psql:
  -- 1. Create user in auth.users (via GoTrue API or Supabase dashboard)
  -- 2. Assign admin role:
  INSERT INTO public.user_roles (user_id, role) 
  VALUES ('<user-uuid>', 'admin');

  -- 3. Assign plant:
  INSERT INTO public.user_plants (user_id, plant_code) 
  VALUES ('<user-uuid>', '1300');

Step 9: Configure Roles & Workflow (NEW)
────────────────────────────────────────
  After logging in as admin:
  
  1. Go to "Role Management" page:
     - Add roles (e.g., Quality, Purchase, Engineering)
     - Role keys are auto-generated from role names
     - Enable "Workflow" toggle for roles that participate in MRB routing
     - Set workflow_status for each role (e.g., quality_review, purchase_review)

  2. Go to "Workflow Config" page:
     - Select a plant
     - Workflow-enabled roles auto-populate
     - Drag to reorder the approval sequence
     - Save the workflow routing

  These configurations drive the entire MRB approval flow dynamically.

6. DATABASE SETUP & MIGRATIONS
================================================================================

Applying migrations safely:
──────────────────────────
  # Automatic (recommended):
  sudo bash /opt/MRB/scripts/setup-db.sh

  # Manual (one file at a time):
  psql "$SUPABASE_DB_URL" -f supabase/migrations/YYYYMMDDHHMMSS_name.sql --single-transaction

  The --single-transaction flag ensures the entire migration is atomic.
  If any statement fails, the entire migration rolls back.

Key tables and their purposes:
  - profiles              → User profiles (auto-created on signup via trigger)
  - user_roles            → RBAC role assignments (separate from profiles!)
  - user_plants           → Multi-plant user assignments
  - user_security         → Login security (lockout, password expiry)
  - password_history      → Prevents reuse of last 4 passwords
  - departments           → Dynamic role definitions with:
                             • role_key (auto-generated, maps to app_role enum)
                             • is_workflow_enabled (participates in MRB routing)
                             • workflow_status (maps to mrb_status enum)
  - role_permissions      → Dense permission matrix (module_key, can_view, can_edit, plant)
  - plant_workflow_config → Approval sequence per plant (dynamic, UI-managed)
  - sap_api_config        → SAP endpoint configurations with credentials
  - scheduler_lock        → Prevents duplicate scheduler runs
  - mrb_records           → Core MRB data with workflow_routing JSON
  - shop_floor_stock      → Stock data (full-refresh on scheduler sync)
  - inward_inspection_lots → Inspection lot data from SAP

Key database functions:
  - has_role()                 → Check if user has a specific role
  - get_user_role()            → Get user's primary role
  - get_user_plant()           → Get user's primary plant
  - check_login_security()     → Check lockout and password expiry
  - record_failed_login()      → Increment failed attempts, auto-lock
  - reset_failed_login()       → Clear lockout state
  - record_password_change()   → Save to history, update last change date
  - check_password_reuse()     → Validate against last 4 passwords
  - admin_update_user_password()→ Admin password reset (8-10 chars)
  - acquire_scheduler_lock()   → Concurrency control for scheduler
  - release_scheduler_lock()   → Release scheduler lock
  - add_dynamic_column()       → Add columns from SAP field mappings
  - get_table_columns()        → Inspect table schema
  - handle_new_user()          → Trigger: auto-create profile on signup
  - update_updated_at_column() → Trigger: auto-update timestamps

8. PROCESS MANAGEMENT (PM2)
================================================================================

PM2 manages two processes:
  1. mrb-app       → SAP proxy middleware (port 3002)
  2. mrb-scheduler → Standalone sync scheduler (port 3100)

Common PM2 commands:
  pm2 list                    # View all processes
  pm2 logs mrb-app            # View middleware logs
  pm2 logs mrb-scheduler      # View scheduler logs
  pm2 restart mrb-app         # Restart middleware
  pm2 restart mrb-scheduler   # Restart scheduler
  pm2 monit                   # Real-time monitoring
  pm2 save                    # Save process list for reboot

Auto-restart on reboot:
  pm2 startup systemd -u iml --hp /home/iml
  pm2 save

PM2 configuration:
  - Max restarts: 10 (before stopping)
  - Restart delay: 5s (middleware), 10s (scheduler)
  - Scheduler auto-restart: every 6 hours (cron)

9. SCHEDULER CONFIGURATION
================================================================================

The scheduler supports two modes:

Mode 1: Standalone Scheduler (recommended for self-hosted)
──────────────────────────────────────────────────────────
  - Runs as PM2 process (mrb-scheduler)
  - Polls sap_api_config every 60 seconds
  - Triggers sync for configs where:
    • scheduler_enabled = true
    • is_active = true
    • sync_frequency ≠ 'manual'
    • Time since last_sync_at ≥ frequency interval
  - Uses scheduler_lock table to prevent duplicate runs
  - Supports multi-plant: iterates sequentially through scheduler_plants
  - Full refresh strategy: deletes existing records before batch insert
    (prevents reporting duplicates as 'updated')

Mode 2: pg_cron + Edge Function (for cloud deployments)
───────────────────────────────────────────────────────
  - pg_cron calls sap-sync-scheduler edge function every 5 minutes
  - Edge function acquires lock, processes due configs, releases lock

Supported sync frequencies:
  every_5_min, every_15_min, every_30_min, hourly,
  every_6_hours, daily, weekly, manual

Verifying scheduler is working:
  pm2 logs mrb-scheduler --lines 50
  # Look for: "[scheduler] Lock acquired, starting run"

  # Check last sync times:
  psql "$SUPABASE_DB_URL" -c "SELECT config_name, sync_frequency, last_sync_at FROM sap_api_config WHERE scheduler_enabled = true;"

10. SAP API INTEGRATION
================================================================================

Four SAP endpoints are configured in sap_api_config:

┌─────────┬────────────────────────────┬────────┬──────────────────┐
│ Name    │ Middleware Path             │ Method │ Purpose          │
├─────────┼────────────────────────────┼────────┼──────────────────┤
│ MB52    │ /sap/api/mb52              │ POST   │ Stock report     │
│ 343     │ /sap/api/343               │ PUT    │ Unblock material │
│ 344     │ /sap/api/344               │ GET    │ Block material   │
│ ZMRB01  │ /sap/api/zmrb01            │ POST   │ Inward lots      │
└─────────┴────────────────────────────┴────────┴──────────────────┘

Self-hosted connectivity:
  - proxy_tunnel_url in sap_api_config must be set to LAN IP of middleware
    e.g., http://10.10.4.178:3002
  - For Docker-to-host: http://host.docker.internal:3002
    (requires extra_hosts in docker-compose.yml)
  - Browser makes direct fetch to middleware (no Edge Function proxy)
  - Middleware enforces 30s timeout, handles non-JSON SAP responses

Dynamic field mapping:
  - Request fields: sap_api_request_fields table
  - Response fields: sap_api_response_fields table
  - Supports map_to_table and map_to_column for auto-insertion
  - add_dynamic_column RPC creates columns if they don't exist

11. RBAC & DYNAMIC ROLE/WORKFLOW MANAGEMENT (UPDATED 2026-04-07)
================================================================================

Architecture Change:
  Previously, roles and workflow steps were hardcoded in the frontend.
  Now, everything is DYNAMIC and driven from the database.

How it works:

  1. DEPARTMENTS TABLE (= Role Definitions)
     ──────────────────────────────────────
     The `departments` table acts as the role registry:
     
     ┌────────────────────┬──────────────────────────────────────────┐
     │ Column             │ Purpose                                  │
     ├────────────────────┼──────────────────────────────────────────┤
     │ name               │ Display name (e.g., "Quality")           │
     │ role_key           │ Maps to app_role enum (auto-generated)   │
     │ is_active          │ Whether role is active                   │
     │ is_workflow_enabled│ Participates in MRB approval routing     │
     │ workflow_status    │ Maps to mrb_status (e.g., quality_review)│
     │ description        │ Optional role description                │
     └────────────────────┴──────────────────────────────────────────┘

  2. DYNAMIC DEPARTMENT MAP HOOK
     ──────────────────────────────
     The `useDepartmentMap` hook (src/hooks/useDepartmentMap.ts) provides:
     - deptToRole: Maps department name → app_role enum value
     - roleToDept: Maps app_role → display name
     - deptToStatus: Maps department name → mrb_status

  3. WORKFLOW ROUTING CONFIG
     ────────────────────────
     The `plant_workflow_config` table defines approval sequences per plant.
     The "Workflow Config" page auto-populates with workflow-enabled roles
     and allows drag-to-reorder.

  4. WORKLIST ROLE FILTER
     ─────────────────────
     The Worklist page's "Pending With" filter is now a dynamic "Role"
     dropdown populated from workflow-enabled departments.

10 application roles (app_role enum):
  quality, quality_head, purchase, purchase_head,
  engineering, engineering_head, shop_floor,
  executive, admin, mrb_committee

Permission model:
  - role_permissions table: (role, module_key, can_view, can_edit, plant)
  - Admin role bypasses all checks
  - Plant-specific filtering: user sees only their plant's data
  - Master Admin (masteradmin@sharviinfotech.com) has additional SAP access

Screen access keys:
  dashboard_kpi, mrb_worklist, material_blocking, inward_materials,
  mrb_print, email_log, help_support, analytics_dashboard,
  quality_dashboard, purchase_dashboard, engineering_dashboard,
  executive_summary

Post-deployment setup:
  1. Log in as admin
  2. Go to "Role Management" → add/edit roles with workflow toggle
  3. Go to "Workflow Config" → arrange approval sequence per plant
  4. Go to "User Management" → assign roles and plants to users
  5. Go to "User Permission Matrix" → set module access per role

14. TROUBLESHOOTING
================================================================================

PROBLEM: Frontend shows blank page
  → Check: ls /opt/MRB/frontend/dist/index.html
  → Check: nginx -t && systemctl status nginx
  → Check: Browser console for JS errors

PROBLEM: "SAP Fetch Failed" on Material Blocking
  → Verify: pm2 status mrb-app (should be "online")
  → Verify: MB52 config exists in sap_api_config with is_active=true
  → Verify: proxy_tunnel_url matches middleware LAN IP
  → Test: curl http://localhost:3002/health

PROBLEM: Scheduler not running syncs
  → Check: pm2 logs mrb-scheduler
  → Verify: scheduler_enabled=true AND is_active=true in sap_api_config
  → Verify: sync_frequency is NOT 'manual'
  → Check: SELECT * FROM scheduler_lock; (clear stale locks)
  → Check: last_sync_at vs current time vs frequency

PROBLEM: Login fails / "Account locked"
  → Check: SELECT * FROM user_security WHERE user_id='<uuid>';
  → Fix: UPDATE user_security SET failed_login_attempts=0, locked_until=NULL WHERE user_id='<uuid>';

PROBLEM: Workflow steps not showing in Workflow Config
  → Check: departments table has roles with is_workflow_enabled=true
  → Check: departments.role_key matches valid app_role enum values
  → Fix: Go to Role Management → enable Workflow toggle for needed roles

PROBLEM: Worklist "Role" dropdown empty
  → Same fix as above: ensure departments have is_workflow_enabled=true

PROBLEM: MRB stuck at wrong approval stage
  → Check: plant_workflow_config for the plant
  → Check: mrb_records.pending_with matches expected role
  → Check: workflow_routing JSON on the MRB record

PROBLEM: PM2 processes not starting after reboot
  → Fix: pm2 startup systemd -u iml --hp /home/iml
  → Fix: pm2 save

PROBLEM: SAP 401 authentication error
  → Check credentials in sap_api_config (username, encrypted_password)
  → Verify sap_client value matches SAP system

PROBLEM: Mixed Content errors (HTTPS → HTTP)
  → The frontend MUST be served from HTTP (same protocol as self-hosted Supabase)
  → Access via http://10.10.4.178:3000, NOT https://
  → Browser blocks HTTPS pages from calling HTTP APIs

PROBLEM: Supabase API not reachable
  → Verify Docker containers are running: docker ps | grep supabase
  → Check Kong gateway: curl http://localhost:8000/rest/v1/
  → Restart: cd /opt/supabase/docker && docker compose restart

PROBLEM: Edge Functions fail with "host.docker.internal" error
  → Add to docker-compose.yml functions service:
    extra_hosts: ["host.docker.internal:host-gateway"]
