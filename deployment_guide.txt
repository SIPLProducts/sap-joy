1. OVERVIEW & ARCHITECTURE
================================================================================

The HBL MRB system consists of these components:

┌─────────────────────────────────────────────────────────────────────┐
│  Browser (React SPA)                                                │
│  └──> Nginx (port 3000) ──> static files from /opt/MRB/frontend/dist│
│  └──> Direct fetch to SAP middleware (port 3002)                    │
│  └──> Supabase API (port 8000) for auth, database, realtime        │
├─────────────────────────────────────────────────────────────────────┤
│  SAP Proxy Middleware  (Node.js, port 3002)                         │
│  └──> Forwards requests to SAP RFC/BAPI endpoints                  │
│  └──> Protected by x-proxy-secret header                           │
├─────────────────────────────────────────────────────────────────────┤
│  Standalone Scheduler  (Node.js, port 3100)                         │
│  └──> Polls sap_api_config for due syncs                           │
│  └──> Uses scheduler_lock to prevent duplicates                    │
│  └──> Supports multi-plant execution                               │
├─────────────────────────────────────────────────────────────────────┤
│  Supabase (Self-Hosted Docker)                                      │
│  └──> PostgreSQL (port 5432)                                       │
│  └──> PostgREST API (port 8001) via Kong Gateway (port 8000)       │
│  └──> Edge Functions (port 9000)                                   │
│  └──> GoTrue Auth                                                  │
└─────────────────────────────────────────────────────────────────────┘

Key Feature Summary:
  - SAP API integration (MB52, 343, 344, ZMRB01) with dynamic field mapping
  - Manual sync + automated scheduler with configurable frequency
  - Multi-plant support with plant switcher
  - Role-based access control (10 roles) via role_permissions table
  - Predefined workflow routing per plant
  - MRB approval sequences with department-level routing
  - Pending actions with 7-day SLA logic
  - Material blocking/unblocking via SAP 343/344 APIs
  - MB52 live fetch (no local storage)
  - Email logging and template management
  - Print configuration per plant

4. FRESH INSTALLATION (Step-by-Step)
================================================================================

Prerequisites:
  - Root or sudo access
  - Self-hosted Supabase already running (or external Supabase project)
  - SAP middleware source files available

Step 1: Transfer files to server
─────────────────────────────────
  # From your local machine:
  scp -r ./project-root iml@10.10.4.178:/tmp/mrb-source

  # Or clone from git:
  ssh iml@10.10.4.178
  git clone <repo-url> /tmp/mrb-source

Step 2: Run the installer
─────────────────────────
  cd /tmp/mrb-source
  sudo bash deploy/install.sh

  This will:
  ✓ Install Node.js 20, PM2, Nginx, Deno
  ✓ Create /opt/MRB directory structure
  ✓ Copy application files
  ✓ Generate template .env file
  ✓ Build the frontend
  ✓ Configure Nginx on port 3000
  ✓ Set correct file permissions

Step 3: Configure environment
─────────────────────────────
  sudo nano /opt/MRB/.env

  Fill in ALL values (see Section 5 for details).

Step 4: Setup database
──────────────────────
  sudo bash /opt/MRB/frontend/deploy/setup-db.sh

  This will:
  ✓ Enable required PostgreSQL extensions
  ✓ Apply all migration files in order
  ✓ Verify all 27 tables exist
  ✓ Verify all 13+ database functions exist

Step 5: Start services
──────────────────────
  sudo -u iml bash /opt/MRB/frontend/deploy/start.sh

  This will:
  ✓ Start SAP middleware on port 3002
  ✓ Start standalone scheduler on port 3100
  ✓ Save PM2 process list for reboot persistence

Step 6: Setup scheduler auto-start
───────────────────────────────────
  sudo bash /opt/MRB/frontend/deploy/setup-scheduler.sh

  This will:
  ✓ Configure PM2 to auto-start on boot
  ✓ Install cron job for stale lock cleanup
  ✓ Optionally setup pg_cron job

Step 7: Verify installation
───────────────────────────
  sudo bash /opt/MRB/frontend/deploy/health-check.sh

  Expected output: All checks should show ✓

Step 8: Create admin user
─────────────────────────
  Access the application at http://<SERVER_IP>:3000
  The first user must be created via Supabase dashboard or SQL:

  -- In psql:
  -- 1. Create user in auth.users (via GoTrue API or Supabase dashboard)
  -- 2. Assign admin role:
  INSERT INTO public.user_roles (user_id, role) 
  VALUES ('<user-uuid>', 'admin');

  -- 3. Assign plant:
  INSERT INTO public.user_plants (user_id, plant_code) 
  VALUES ('<user-uuid>', '1300');

6. DATABASE SETUP & MIGRATIONS
================================================================================

Applying migrations safely:
──────────────────────────
  # Automatic (recommended):
  sudo bash /opt/MRB/frontend/deploy/setup-db.sh

  # Manual (one file at a time):
  psql "$SUPABASE_DB_URL" -f supabase/migrations/YYYYMMDDHHMMSS_name.sql --single-transaction

  The --single-transaction flag ensures the entire migration is atomic.
  If any statement fails, the entire migration rolls back.

Key tables and their purposes:
  - profiles           → User profiles (auto-created on signup)
  - user_roles         → RBAC role assignments (separate from profiles!)
  - user_plants        → Multi-plant user assignments
  - role_permissions    → Dense permission matrix (module_key, can_view, can_edit, plant)
  - plant_workflow_config → Predefined workflow routing per plant
  - sap_api_config      → SAP endpoint configurations with credentials
  - scheduler_lock      → Prevents duplicate scheduler runs

Production fix for role_permissions:
  If you encounter error 23502 on the screen_key column:
  ALTER TABLE public.role_permissions ALTER COLUMN screen_key DROP NOT NULL;

8. PROCESS MANAGEMENT (PM2)
================================================================================

PM2 manages two processes:
  1. mrb-app       → SAP proxy middleware (port 3002)
  2. mrb-scheduler → Standalone sync scheduler (port 3100)

Common PM2 commands:
  pm2 list                    # View all processes
  pm2 logs mrb-app            # View middleware logs
  pm2 logs mrb-scheduler      # View scheduler logs
  pm2 restart mrb-app         # Restart middleware
  pm2 restart mrb-scheduler   # Restart scheduler
  pm2 monit                   # Real-time monitoring
  pm2 save                    # Save process list for reboot

Auto-restart on reboot:
  pm2 startup systemd -u iml --hp /home/iml
  pm2 save

PM2 configuration:
  - Max restarts: 10 (before stopping)
  - Restart delay: 5s (middleware), 10s (scheduler)
  - Scheduler auto-restart: every 6 hours (cron)

9. SCHEDULER CONFIGURATION
================================================================================

The scheduler supports two modes:

Mode 1: Standalone Scheduler (recommended for self-hosted)
──────────────────────────────────────────────────────────
  - Runs as PM2 process (mrb-scheduler)
  - Polls sap_api_config every 60 seconds
  - Triggers sync for configs where:
    • scheduler_enabled = true
    • is_active = true
    • sync_frequency ≠ 'manual'
    • Time since last_sync_at ≥ frequency interval
  - Uses scheduler_lock table to prevent duplicate runs
  - Supports multi-plant: only syncs plants in scheduler_plants array

Mode 2: pg_cron + Edge Function (for cloud deployments)
───────────────────────────────────────────────────────
  - pg_cron calls sap-sync-scheduler edge function every 5 minutes
  - Edge function acquires lock, processes due configs, releases lock

Supported sync frequencies:
  every_5_min, every_15_min, every_30_min, hourly,
  every_6_hours, daily, weekly, manual

Verifying scheduler is working:
  pm2 logs mrb-scheduler --lines 50
  # Look for: "[scheduler] Lock acquired, starting run"

  # Check last sync times:
  psql "$SUPABASE_DB_URL" -c "SELECT config_name, sync_frequency, last_sync_at FROM sap_api_config WHERE scheduler_enabled = true;"

Preventing duplicate execution:
  The scheduler_lock table with a unique lock_key constraint ensures
  only one scheduler instance runs at a time. Stale locks (>10 min)
  are automatically cleaned by the cron job.

10. SAP API INTEGRATION
================================================================================

Four SAP endpoints are configured in sap_api_config:

┌─────────┬────────────────────────────┬────────┬──────────────────┐
│ Name    │ Middleware Path             │ Method │ Purpose          │
├─────────┼────────────────────────────┼────────┼──────────────────┤
│ MB52    │ /sap/api/mb52              │ POST   │ Stock report     │
│ 343     │ /sap/api/343               │ PUT    │ Unblock material │
│ 344     │ /sap/api/344               │ GET    │ Block material   │
│ ZMRB01  │ /sap/api/zmrb01            │ POST   │ Inward lots      │
└─────────┴────────────────────────────┴────────┴──────────────────┘

MB52 special behavior:
  - Data is fetched LIVE (not stored in Supabase)
  - No "Trigger Sync" button on SAP Sync Monitor
  - Shows "Live Fetch" badge
  - Used by Material Blocking page for real-time stock data

343/344 special behavior:
  - Marked as "Action API" in Sync Monitor
  - No scheduling (manual trigger only)
  - 343: Moves blocked stock to unrestricted
  - 344: Moves unrestricted stock to blocked

Dynamic field mapping:
  - Request fields: sap_api_request_fields table
  - Response fields: sap_api_response_fields table
  - Supports map_to_table and map_to_column for auto-insertion
  - add_dynamic_column RPC creates columns if they don't exist

Authentication:
  - Credentials stored in sap_api_config (username, encrypted_password)
  - Multi-strategy fallback: Basic Auth → header aliases → query params
  - SAP client passed as sap-client header and URL parameter

Testing connectivity:
  - Use "Test Route" button in SAP Sync Monitor
  - Checks: middleware reachable → SAP auth valid → response parseable

14. TROUBLESHOOTING
================================================================================

PROBLEM: Frontend shows blank page
  → Check: ls /opt/MRB/frontend/dist/index.html
  → Check: nginx -t && systemctl status nginx
  → Check: Browser console for JS errors

PROBLEM: "SAP Fetch Failed" on Material Blocking
  → Verify: pm2 status mrb-app (should be "online")
  → Verify: MB52 config exists in sap_api_config with is_active=true
  → Verify: proxy_tunnel_url matches middleware LAN IP
  → Test: curl http://localhost:3002/health

PROBLEM: Scheduler not running syncs
  → Check: pm2 logs mrb-scheduler
  → Verify: scheduler_enabled=true AND is_active=true in sap_api_config
  → Verify: sync_frequency is NOT 'manual'
  → Check: SELECT * FROM scheduler_lock; (clear stale locks)
  → Check: last_sync_at vs current time vs frequency

PROBLEM: Login fails / "Account locked"
  → Check: SELECT * FROM user_security WHERE user_id='<uuid>';
  → Fix: UPDATE user_security SET failed_login_attempts=0, locked_until=NULL WHERE user_id='<uuid>';

PROBLEM: "23502 null value in column screen_key"
  → Fix: ALTER TABLE role_permissions ALTER COLUMN screen_key DROP NOT NULL;

PROBLEM: PM2 processes not starting after reboot
  → Fix: pm2 startup systemd -u iml --hp /home/iml
  → Fix: pm2 save

PROBLEM: SAP 401 authentication error
  → Check credentials in sap_api_config (username, encrypted_password)
  → Verify sap_client value matches SAP system
  → Try: Update credentials via SAP API Settings UI

PROBLEM: Duplicate scheduler executions
  → Check: SELECT * FROM scheduler_lock;
  → Ensure only ONE scheduler is running: pm2 list
  → If using both pg_cron and standalone, disable one

PROBLEM: Missing sidebar menu items
  → Check: role_permissions for the user's role and plant
  → Verify: can_view=true for the module_key
  → Admin role sees everything regardless

15. SECURITY CHECKLIST
================================================================================

  [ ] .env file has chmod 600 and owned by iml
  [ ] SUPABASE_SERVICE_ROLE_KEY never in frontend code
  [ ] SAP_PROXY_SECRET is strong and unique
  [ ] Nginx listens only on required ports
  [ ] UFW firewall enabled:
        sudo ufw allow 3000/tcp    # Frontend
        sudo ufw allow 22/tcp      # SSH
        sudo ufw enable
  [ ] PostgreSQL not exposed to internet (only LAN)
  [ ] RLS policies enabled on all tables
  [ ] user_roles table separate from profiles (no privilege escalation)
  [ ] Password policy: 8-10 chars, expiry 45 days, max 5 failed attempts
  [ ] Password history: prevents reuse of last 4 passwords
  [ ] Account lockout: 30 minutes after max failed attempts
  [ ] No hardcoded credentials in source code
  [ ] SAP credentials stored in database, not in files
